# Features and background work

Details moved out of the README. Each paragraph describes one area of the app.

**Job finder** (sidebar) pulls remote PHP/Laravel listings into a review list. Each source has its own worker: the Himalayas search API, We Work Remotely's programming RSS feeds, and, by scraping their pages, Wellfound and Built In (these two can block or break without notice and may be against those sites' terms; use at your own discretion). Runs start only from the buttons on the page and never on a schedule. A run makes at most `SCRAPER_MAX_PAGES` requests (default 3) per source, `SCRAPER_SPACING` seconds apart (default 5), only one run can be queued or running at a time, and any refusal (403, 429, timeouts) ends that run immediately. Listings that mention none of the `config/scrapers.php` keywords, junior/intern titles, listings restricted to places outside the US (`allowed_regions`; ones with no restriction are labelled Worldwide), and links already staged or tracked are skipped. Found listings wait on the page: tick any number of rows (the ticks survive paging) and press Add selected listings to save them through the normal save path, with the source named and every field the site gave (company page, location, eligible countries and time zones, pay, requirements, notes, posting date and expiry); the selection is cleared afterwards and unticked listings stay. Pay in another currency is converted to US dollars when a listing is staged, at the fixed approximate rates in `config/scrapers.php` (`usd_rates`; a currency not listed is left as posted), with the original figures kept in the pay notes. The sort and filter choices stay in the page address. Both the review list and the overview can be sorted by pay (hourly, monthly and other periods are scaled to a year, currencies are not converted, unknown pay last) and by location (US first, then Worldwide, then A–Z); the review list also sorts by posting date. Dismissed ones are remembered and not found again.

**Queue** (sidebar) is one page for background work, with an All / Link checks / Grading filter (kept in the URL; `/link-checks` and `/scoring` redirect to it). The two sections below describe what each does. **Link checks** fetch an application page in the background to see whether it is still live (404/410 are flagged as gone, and so are pages that load but say the job is gone, such as "job not found", or whose structured data has expired; sites that refuse automated requests, such as LinkedIn, are flagged as blocked) and fill in only the fields that are still empty from the page's structured job data (schema.org JobPosting). Links on Ashby, Greenhouse and Lever are checked through those companies' public job-board APIs instead of their pages (the pages are JavaScript shells that answer 200 even for a closed job), which also fills title, location, pay and the description. Nothing existing is overwritten. A job whose link is gone (404/410) is closed automatically, unless it is already applied or past the saved/preparing stages; other failures are only flagged. Check one job from its page, all active jobs from the log page, or paste job page links on the Import page to create new listings from them. The log page can clear finished entries (older than 30 or 7 days, or all); queued and running checks and ones whose AI request is running are kept, a waiting AI request is cancelled with its check, and jobs are never touched. Checks are spaced a few seconds apart (`LINKCHECK_SPACING`), never run on a schedule, and refuse private or reserved network addresses.

**Saved pages and pasted text.** The Import page also has *Add from a saved page or text* (one file box: `.csv`/`.tsv` start the CSV import, `.html`/`.htm`/`.mhtml`/`.mht`/`.txt` are imported as a posting): save a job page in your browser (HTML or MHTML), or paste the posting text, and import it with no network request. Structured job data is read at once; otherwise the text is kept and queued for AI reading. Choose an existing job to fill its empty fields, or leave it empty to create a new listing. PDF files are not read yet (no PDF text tool is installed).

**Render page.** Pages that build their content with JavaScript give the plain fetch almost no text. *Read with AI* on a fetched row first queues a browser render of its link, and the AI pass waits for it (and still runs on the old text if the render fails): the host bridge (`bin/ai-bridge`) opens the link in headless Chromium through Playwright, waits for the page to settle and replaces the check's saved text with what the browser shows; The AI then reads that text. It is on demand only (never in bulk or on a schedule), skips saved text, and does not load images, media, fonts or stylesheets. All browser traffic, redirects, scripts and WebSockets included, goes through a local filtering proxy (`tools/render/proxy.mjs`) that connects only to the public addresses the app's address guard returns (`php artisan render:allow`), so a name cannot be re-resolved to a private address after it was checked, and localhost and LAN targets are refused. WebRTC is switched off (browser flags plus removing the API from every page) so no UDP can bypass the proxy. Chromium also runs in its own network namespace with only a loopback interface (`tools/render/isolated-chrome.sh`, via unprivileged `unshare`); the proxy listens on a unix socket and a small relay (`relay.mjs`) forwards the namespace's loopback port to it, so the browser has no route anywhere else. `RENDER_ISOLATE=0` falls back to a plain loopback proxy where unprivileged namespaces are unavailable. Chromium runs with its sandbox on (`RENDER_NO_SANDBOX=1` turns it off where unprivileged user namespaces are unavailable). One-time host setup: `cd tools/render && npm install`; it uses the newest Chromium in `~/.cache/ms-playwright` (or `RENDER_CHROME`) and `RENDER_TIMEOUT_MS` (default 30000). `node --test` in `tools/render` runs the proxy tests. The systemd unit below runs it.

**Read with AI.** When a live page has no structured data, the link-check log keeps its readable text (the text is kept for every fetched page, with or without structured data, so you can also request an AI pass on a page whose structured data was incomplete; a pass fills empty fields and may replace the long text fields (benefits, responsibilities, requirements, hours), keeping the earlier values under *Replaced earlier values* in the log. Pages read through a job-board API keep the posting text the API returned) (capped by `LINKCHECK_MAX_TEXT_CHARS`) and offers a *Read with AI* button. Clicking it queues one request (`ai_requests`) and the row shows its state (waiting for the bridge, reading, then the result or the failure reason; the page refreshes itself, and a failed request can be retried, and the model's raw reply is kept and shown under *Raw reply*); nothing runs in bulk or on a schedule. A host-side bridge (`bin/ai-bridge`, needs `docker`, `jq` and `sessioneer` with `--wait` and `--no-tools` on the host; run it by hand, or with `--loop`; `docker/jacker-ai-bridge.service` is a systemd user unit that runs the loop: symlink it into `~/.config/systemd/user/`, edit the `ExecStart` path to your checkout, then `systemctl --user daemon-reload && systemctl --user enable --now jacker-ai-bridge`) takes queued requests through `php artisan ai:claim`, runs each one through the agent chain in `config/ai.php` (Claude Haiku via a one-off Sessioneer session started with `--no-tools`, then Codex in a read-only sandbox, then opencode with its tools denied; an agent with no quota or an error falls through to the next, `AI_MODEL`, `AI_CODEX_MODEL` and `AI_OPENCODE_MODEL` set the models, and the bridge skips any entry that is not one of those three agents with a plain model name) and returns the first usable reply, and which agent gave it, through `php artisan ai:complete <id>`, so a posting that tries to give the model instructions cannot make it run anything; the prompt also says the page is data only and the page cannot close the text fence early. Only valid job fields are accepted, and only empty fields of the job are filled, apart from the long text fields an AI pass may replace.

**Settings** (sidebar) hold these things. *Profile links* are an optional LinkedIn and GitHub address (https, on linkedin.com / github.com) shown in the top bar when set; a blank field hides it. *PDF header* (name, email, phone, location; blank lines are left out) and *Cover letter AI* (agent claude, codex or opencode, a plain model name and a thinking level off, low, medium or high) belong to cover letters, below. *Grading criteria* edit the criteria below without touching code: the skill-match rubric, the pay weight, points for unknown pay, the Eastern-hours penalty, the pay bands and the points per work arrangement. They are stored in the `settings` table (`ScoringSettings`, falling back to `config/scoring.php`); *Reset to defaults* deletes them. Changes apply to the next grading run.

**Cover letters.** Each job has one letter on its detail page: paste the text or import a .txt / .md file, edit it and save (a blank save removes it). Nothing is sent anywhere. *Download PDF* (`/opportunities/{id}/cover-letter.pdf`, 404 without a letter) renders it with dompdf in a serif font under a header built from the PDF header settings and the profile links. *Suggest improvements with AI* queues an `ai_requests` row of kind `letter`; the host bridge takes it with `php artisan letter:claim`, runs the single agent, model and thinking level saved in Settings (re-checked against the same allowlists, claude through `sessioneer --no-tools`, codex read-only, opencode with tools denied) and stores the plain-text reply with `letter:complete`. The prompt fences the job listing and the letter between marker lines with a fresh random token as data only. The suggestions are kept on the letter with a timestamp (a new run replaces them) and are only displayed: the AI never edits the letter. It needs the bridge running.

**Grading** re-calculates *fit* (skill match) and *want* (desirability) for open listings (not closed, archived or applied). *Score unscored* only takes listings missing a score; *Re-score all open* overwrites every score after a confirmation, and the page keeps each listing's earlier scores in its Before column. Fit is judged from the listing by an AI agent using the rubric in `config/scoring.php`; want is computed in PHP from pay (annualised midpoint, neutral when unknown) and work mode, minus a penalty for Eastern-only hours; by default 60% pay and 40% work mode and one point off, all editable under Grading settings. Requests are `ai_requests` rows of kind `score`, taken by the same host bridge (`php artisan score:claim` / `score:complete`), which tries `config('scoring.chain')` in order (Claude Haiku through `sessioneer --no-tools`, then `codex exec --sandbox read-only` (user config and rules ignored), then `opencode run` with shell, edit, web, subagent, skill and outside-directory access denied and an empty config directory so no MCP servers load; `SCORE_MODEL`, `SCORE_CODEX_MODEL` and `SCORE_OPENCODE_MODEL` change the models) until one returns a JSON reply, so an agent out of quota falls through to the next. *Clear done* removes finished requests; the scores stay. Nothing runs on a schedule.

**Questions** (sidebar) is one list of interview questions to ask, filtered by stage (applied, screening, interviewing, offer; the stage is the opportunity status). Add, edit, reorder or delete them there, optionally with predefined answers (one per line). Each opportunity has a *Questions* page (button on its detail page) where you record the answers as you go; it opens on the job's current status, and clearing a field means the question does not apply. A job in *Recruiter contact* (a recruiter reached out before you applied; not counted as applied, and the company field can hold the recruiter's name until you know the employer) opens on the screening questions. The initial list is loaded once with `php artisan db:seed --class=InterviewQuestionSeeder`.
